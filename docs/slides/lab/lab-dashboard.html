What is a dashboard, really?

A dashboard is a report that responds. A static report shows one fixed view of your results. A dashboard lets the viewer choose what they see — which variable, which time period, which model — without you rebuilding anything.

Definition

A dashboard is a document organized into cards, arranged in rows and columns, optionally with controls (dropdowns, sliders) that let the viewer change what’s displayed.

Four moving pieces, in every dashboard you’ll ever build:

  1. Data — what you’re showing
  2. Computation — what you did to it (a model, a test, a summary)
  3. Layout — how it’s arranged on the page
  4. Interactivity (optional, but what makes it a dashboard and not just a report)

Why Quarto, specifically

There are other dashboard tools — Streamlit, Dash, Shiny — but they require a running server and a framework you’d need to learn from scratch.

Quarto dashboards are static

No server. quarto render produces a self-contained HTML file — the same thing that happens when you render a slide deck or the textbook. Deploy it to GitHub Pages exactly like your Week 4 website.

Same .qmd files, same code cells, same # %%-adjacent authoring experience — just a different format: in the YAML.

Build increment 1 — the skeleton

The YAML: one new key

---
title: "ECON-5371 Project Dashboard"
subtitle: "Reference example — Vector Autoregression"
author: "Your Name"
format: dashboard
---

format: dashboard is the only thing that turns a normal .qmd into a dashboard. Everything else about writing code cells stays exactly what you already know.

Rows, and your first value boxes

## headings become rows. Inside a row, a code cell with #| content: valuebox becomes a compact stat card.

```{python}
#| content: valuebox
#| title: "Observations"
#| icon: calendar3
#| color: primary
import pandas as pd

df = pd.read_csv("data/macro_var_synthetic.csv", parse_dates=["date"])
dict(value=len(df))
```

The mechanic

A value box cell returns a Python dict — Quarto reads its keys (value, icon, color) to build the box. icon names come from the free Bootstrap Icons library.

What we actually saw when we rendered this

Three value boxes — stretched to fill the entire screen height, not a compact strip.

Why: a dashboard with one row always fills 100%

Quarto splits page height across however many rows exist. With only one row — even set to height=20% — there’s nothing else to claim the remaining 80%, so Quarto expands the one row to fill everything. This isn’t a bug. It’s relative sizing with nothing to divide.

The fix wasn’t in this row at all — it was adding a second row. Row heights only make sense relative to each other.

Build increment 2 — a plot card

Adding the time-series plot

```{python}
#| title: "Output Gap, Inflation, and Policy Rate"
import matplotlib.pyplot as plt

plt.rcParams['figure.figsize'] = (11, 4)

fig, ax = plt.subplots()
for var in ["output_gap", "inflation", "policy_rate"]:
    ax.plot(df["date"], df[var], label=var, linewidth=1.2)
ax.legend(loc="upper left", frameon=False)
plt.show()
```

Matplotlib doesn’t auto-resize

Unlike interactive plotting libraries, a static matplotlib figure doesn’t stretch to fit its card. Set the figure size explicitly — plt.rcParams['figure.figsize'] — sized for how wide the card will actually be.

Three rows in, cramped again

Once we added a third row — a table and two value boxes — the page looked squeezed again. A “Date Range” box even had its text clipped, cut off mid-number.

Same root cause, compounding

Row 1 and Row 2 had explicit heights (20% / 80%) that summed to 100% — fine for two rows. Adding a third row with no height specified meant Quarto tried to fit 20% + 80% + (undefined) into one page. The undefined row got squeezed, and so did everything else.

The fix: audit your total every time you add a row

We rebalanced to 15% / 55% / 30% — three numbers that actually sum to 100%. Every time you add a row to a dashboard, re-check that all your row heights on that page still add up.

Build increment 3 — columns and a table

Splitting a row into columns

### headings, nested under a ## Row, split that row into columns — one level down from how rows split the page.

## Row {height=30%}

### Column {width=60%}
... stationarity table ...

### Column {width=40%}
... lag order and stability value boxes ...

Same nesting logic throughout Quarto dashboards: page → rows → columns → cards. One heading level per layer.

A results table with tabulate

```{python}
#| title: "Stationarity (ADF Test)"
from statsmodels.tsa.stattools import adfuller
from tabulate import tabulate
from IPython.display import Markdown

rows = []
for var in variables:
    result = adfuller(df[var], autolag="AIC")
    verdict = "Stationary" if result[1] < 0.05 else "Unit root"
    rows.append([var, f"{result[0]:.3f}", f"{result[1]:.4f}", verdict])

adf_table = pd.DataFrame(rows, columns=["Variable", "ADF Stat", "p-value", "Result"])
Markdown(tabulate(adf_table, showindex=False, headers=adf_table.columns))
```

tabulate turns a small DataFrame into a clean markdown table; wrapping it in Markdown(...) tells Quarto to render it as formatted text, not print raw markdown syntax to the page.

One more content problem: text that overflows its box

Even after fixing row heights, one value box still showed clipped text: "1985–2024" wrapped onto two lines, and the second line got cut off by the box’s own height.

Value boxes expect short content

A value box is built for a glanceable number or short label — not a long string. "1985–2024" (9 characters) was too wide to stay on one line at that font size.

The fix: shorten the content, don’t fight the box

We changed the display to '85–'24 — a compact year format that fits on one line. When a value box’s content doesn’t fit, shortening what you’re displaying is usually the right move, not resizing the box indefinitely.

Build increment 4 — a second page, and tabs

Multiple pages: # headings

A level-1 heading (#, not ##) starts a new page — appearing as a link in the dashboard’s navbar.

# Overview
... everything so far ...

# Model Results
... Granger causality, IRFs, FEVD ...

Confirmed: state carries across pages

Variables defined in Page 1’s Python cells (df, variables) were still available in Page 2’s cells, without re-importing or re-loading anything. One shared Python session for the whole document.

Tabs: .tabset on a row

Three results — Granger causality, impulse responses, variance decomposition — don’t need to compete for space on one page. A tabset lets the viewer click between them.

## Row {.tabset height=100%}

```{python}
#| title: "Granger Causality"
... table ...
```

```{python}
#| title: "Variance Decomposition"
... plot ...
```

Two cells, .tabset on the row — this should produce two tabs.

What we actually got: four tabs, not three

A dropdown-plus-image pair, meant to be one tab (“Impulse Responses”), rendered as two separate tabs instead.

Why: #| title: labels one cell, not a group

Inside a .tabset, every individual cell becomes its own tab by default. #| title: names that one cell’s tab — it doesn’t merge multiple cells into a single tab, even if you intend them to belong together.

The fix: ### headings group cells into tabs

## Row {.tabset height=100%}

### Granger Causality
```{python}
... one cell ...
```

### Impulse Responses
```{ojs}
... dropdown cell ...
```
```{ojs}
... image cell ...
```

A ### heading starts a new tab; every cell underneath it, however many, belongs to that same tab. This is the same row → column → card nesting pattern from Build Increment 3, one more layer deep.

General lesson

When a Quarto layout container (tabset, columns, rows) needs to hold more than one cell as a single unit, reach for an explicit heading to group them — don’t rely on a single cell’s own title option.

Build increment 5 — real interactivity

What makes this a dashboard, not a report

Everything so far is static — the same output every time, regardless of who’s looking at it. A dropdown that changes what’s displayed is the feature that actually earns the word “dashboard.”

Observable JS ({ojs})

A second language Quarto supports alongside Python, running in the viewer’s browser — no server required. This keeps a dashboard deployable as plain static HTML, same as GitHub Pages.

A dropdown that swaps an image

```{python}
#| output: false
# Generate one IRF panel image per shock variable, saved to images/
# (full code: one matplotlib figure per shock, saved as a PNG)
```
```{ojs}
viewof shock_choice = Inputs.select(
  ["output_gap", "inflation", "policy_rate"],
  {{label: "Shock to:", value: "output_gap"}}
)
```
```{ojs}
html`<img src="images/irf_${{shock_choice}}.png" style="width: 100%;">`
```

viewof creates both the visible dropdown and a reactive variable, shock_choice. Any {ojs} cell referencing it re-runs automatically the moment the dropdown changes.

Why images, not a live recomputation

A deliberate simplification

Connecting Python-computed values directly into {ojs} (via ojs_define()) is possible, but stacks several new, untested concepts at once. Pre-generating one image per option and letting the dropdown just swap which image shows is simpler, safer, and still genuinely interactive.

This worked on the first render — no gotcha here, for once.

Build increment 6 — UTEP branding

A theme file, same pattern as the slides

Dashboard theming uses the same SCSS structure as eo-slides.scss: scss:defaults for variables, scss:rules for fine-grained CSS.

/*-- scss:defaults --*/
$utep-orange: #FF8200;
$utep-blue:   #041E42;
$utep-silver: #B1B3B3;

@import url('https://fonts.googleapis.com/css2?family=Crimson+Pro...');

$primary:   $utep-blue;
$secondary: $utep-silver;
$navbar-bg: $utep-blue;
$navbar-fg: #FFFFFF;
format:
  dashboard:
    theme: [cosmo, dashboard-theme.scss]

UTEP’s current brand fonts

Crimson Pro for headings and titles, Inter for body text — both freely available via Google Fonts, so no fallback substitution is needed.

Mapping value box colors to the brand

color: primary and color: secondary now resolve to UTEP Blue and Silver automatically, once set in the theme file. For Orange — not a default Bootstrap slot — use the hex value directly:

#| color: "#FF8200"

Result: every value box on the page uses only Blue, Silver, and Orange — no leftover Bootstrap cyan or green.
